The feature under analysis: Add Services

Add Services lets a user initiate another ride or service while an existing ride request is still waiting for Captain acceptance. It is a smart answer to passive waiting, but it stops one step short of solving the real pain.

What Add Services solves

Users do not have to wait passively for their first ride request. They can initiate another service while the first request is still pending.

What it doesn't solve

The user still has to manually decide which alternative mode to select, book it, and wait again.

This exact gap is the setup for everything that follows in this teardown.

Slide 05 Problem Framing

Add Services solves waiting.
Does it solve decision fatigue?

When the first request goes unanswered, users can Add Services. But they still have to choose the next mode themselves, repeat the booking, and wait all over again.

Problem statement

The friction loop today

Select mode
↓
Request ride
↓
Wait
↓
No acceptance
↓
Add another service
↓
Select another mode, wait again

The loop repeats until something accepts, or the user gives up.

User impact
  • Reduced certainty: which available mode will actually accept first?
  • Cognitive load: repeatedly comparing modes, price, ETA, and comfort
  • Time wastage: every failed selection starts a new waiting cycle
  • Frustration: repeated decisions make booking feel stressful
Business impact
  • Booking conversion: failed attempts reduce completed rides
  • Retention: repeated friction reduces future usage
  • Competitive leakage: frustrated users switch platforms
  • Marketplace efficiency: available supply gets abandoned across modes
Product hypothesis

If Rapido could automatically search across user-approved ride modes based on user priorities, Add Services could evolve from a manual fallback into an intelligent booking mechanism. This is a hypothesis to validate, not a validated conclusion.

Slide 06 Solution Analysis

From "Add Another Service" to "Book Any"

The proposal is an enhancement, not a reinvention: keep everything users know, and replace the manual fallback with one preference-driven request.

Current journey · manual

Launch app
↓
Select destination
↓
View modes + fare + average wait
↓
Select a ride mode
↓
Wait for Captain acceptance
↓
Use Add Services, manually pick another mode
↓
Wait again, repeat if needed

Pain concentrated in: cognitive load · wait time · repeated decisions

Proposed · Book Any flow

Launch app
↓
Select destination
↓
Tap Book Any
↓
Set preferences: priority (time / budget / comfort) + eligible modes (Bike, Auto, Mini, Prime, Sedan, XL)
↓
Rapido searches eligible modes
↓
First matching Captain accepts → search stops
↓
Ride confirmed

The user defines the trade-off. Rapido handles the search.

How it works · example

Priority TIME · eligible modes AUTO + MINI + PRIME

If no Auto accepts within the defined threshold, Rapido automatically searches the next eligible mode. The moment a Captain accepts anywhere in the set, the search stops and the ride is confirmed. One click stands in for a whole chain of manual fallbacks.

You choose what matters. Rapido chooses what to book.

Slide 07 Solution Analysis

Why Book Any could improve Add Services, and where it could fail

Strengths
  • Reduced cognitive loadOne preference-setting step replaces repeated ride selection.
  • Faster bookingRapido searches across eligible modes instead of making the user restart manually.
  • Preference-based matchingUsers define what matters: time, budget, or comfort.
  • Better supply matchingAvailable supply across multiple eligible modes gets utilised.
  • Compounds for frequent usersThe benefit multiplies for people booking several rides a day.
Risks and weaknesses
  • Preference setup frictionUsers may not want to configure preferences every time.
  • Preference complexityToo many choices could recreate the very cognitive load we are removing.
  • Trade-off conflictsThe cheapest option may not be fastest; the fastest may not be most comfortable.
  • TrustUsers need to know which ride they could receive before confirming.
  • Supply constraintsBook Any cannot manufacture Captains where none exist.
Next iteration idea

Remember my preference

Setup friction falls away for frequent routes. Save a route once, ride it in one tap every time after.

Route Home → Office Priority Fastest Eligible Auto + Bike + Mini Next time: Book Any → one tap

Design principles (derived from the risks)

Principle

Defaults over decisions

Pre-fill preferences from behaviour so Book Any works with zero setup for most rides.

Principle

Small choice set

One priority, a short mode list, one price cap. Every extra control is cognitive load returning through the back door.

Principle

Reversible, always

The specific-mode list stays one scroll away. Book Any never replaces choice; it shortcuts it.

Trust and transparency (non negotiable)

  • Show the menu before confirm: users always see which modes they might get and the price range.
  • No surprises at pickup: the matched mode, fare, and Captain details appear the instant a match is made.
  • Opt in, never default: Book Any is a tap the user chooses, sitting alongside the existing flow it grew out of.
  • Safety preferences travel with the user: constraints like helmet required or top-rated Captains apply across every match, which is what makes Book Any safe for someone like Kanika.

Scope discipline (what I would ship first)

Version 1
  • Book Any with priority plus eligible modes plus price cap
  • Transparent match preview before confirmation
  • Works beside, not instead of, Add Services
Deliberately later
  • Remember my preference for saved routes
  • Finer controls (per-route rules, schedules)
  • Anything that expands the choice set before V1 proves the loop

Slide 08 Success Metrics

How would we know Book Any works?

North Star

Successful Book Any rides per Book Any user per 30 days

One number that captures both usefulness (rides complete) and habit (users come back).

1 · Efficiency Median time to confirmation Time from initial Book Any request to Captain acceptance. Booking attempts per completed ride Average attempts needed to complete a ride.
2 · Conversion Book Any completion rate Completed Book Any rides / total Book Any requests × 100. Book Any cancellation rate Cancelled Book Any bookings / total Book Any bookings × 100.
3 · Retention 30-day Book Any repeat rate Users completing 2+ Book Any rides in 30 days / users completing 1+ × 100. Cohort retention D7D14D21 D30D60D90
4 · Marketplace health Captain acceptance rate Mode-switch rate Median pickup ETA Supply utilisation

How I would validate it (before any big build)

Experiment

A/B test in 2 to 3 high-supply cities where Add Services usage is already strong. Control: today's Add Services flow. Treatment: Book Any as an option beside it. Read time to confirmation, completion rate, and repeat usage, and watch cancellation rate as the guardrail.

Success looks like

Time to confirmation drops and completion rises for the treatment group, without an increase in cancellations or worse marketplace health. If cancellations climb, the trust problem is real and the matching logic, not the UI, is what to fix next.

Add Services removes passive waiting. Book Any could remove the active decision-making needed to recover from a failed booking.
